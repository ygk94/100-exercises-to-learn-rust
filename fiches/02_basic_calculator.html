L'objectif est de savoir expliquer chaque concept à partir des premiers principes, pas seulement de faire passer les tests. Pour chaque notion : le principe, la syntaxe, ce que tu as fait, puis les pièges.

§0Les 5 principes de Rust

Tout le chapitre découle de ces cinq idées. Si tu sais les expliquer, tu sais expliquer le chapitre.

principe 1

Tout a un type connu à la compilation

Typage statique. Le compilateur refuse ce qu'il ne peut pas typer (ex. 09).

principe 2

Rien n'est implicite

u8 ≠ u32 (ex. 01), pas de truthy/falsy (ex. 03), as obligatoire (ex. 10).

principe 3

Immuable par défaut

Un let ne se modifie pas : il faut mut (ex. 06, 07).

principe 4

Presque tout est une expression

Dernière ligne sans ; = valeur de retour. if renvoie une valeur.

principe 5

Pas d'erreur silencieuse sans ton accord

panic! (ex. 04), overflow = panic en dev sauf si tu choisis autre chose (ex. 08, 09).

À savoir dire« Rust déplace un maximum d'erreurs de l'exécution vers la compilation. Le compilateur agit comme un vérificateur de preuves : si le code compile, toute une classe de bugs (types incohérents, variables non initialisées, mutations non prévues, accès mémoire invalides) est impossible. »

§1Le compilateur et ses checkers

Quand tu lances cargo build ou cargo test, rustc fait passer ton code par plusieurs vérifications successives. Tu en as croisé plusieurs dans ce chapitre.

1

Parsing

La syntaxe est-elle correcte ? Accolades, ;, mots-clés.

2

Résolution de noms

factorial existe-t-il ? Vers quoi pointe use crate::speed ?

3

Type checker

Chaque expression a-t-elle un type cohérent ? E0308 E0689

4

Borrow checker

Initialisation, mutabilité, ownership, emprunts respectés ? E0381 E0384 E0382

5

Lints

Avertissements : unused import, overflowing_literals, dead_code…

6

Code machine + checks à l'exécution

Overflow, division par zéro → panic.

Le type checker : erreurs rencontrées

ErreurOùExplication
E0308 expected u32, found u8ex. 01a + b * multiplier avec multiplier: u8 : les opérateurs exigent deux opérandes du même type. Aucune promotion automatique.
E0308 expected bool, found integercours 03if number { } est interdit : la condition doit être un bool.
E0689 ambiguous numeric type {integer}ex. 09Appel de méthode sur un entier dont le type n'est pas encore fixé. Voir ci-dessous.

Inférence : pourquoi let mut result: u32 = 1; (ex. 09)

  • Un littéral 1 seul a un type provisoire {integer} : « un entier, je ne sais pas encore lequel ».
  • Le compilateur fixe ce type en regardant les usages (unification).
  • Mais pour appeler une méthode (result.saturating_mul(i)), il doit savoir tout de suite sur quel type la chercher : u8::saturating_mul ? u32::saturating_mul ? Il ne peut pas attendre, d'où E0689.
  • À l'ex. 07 (let mut res = 1; res *= i;), pas besoin d'annotation : *= est un opérateur, et i: u32 plus le -> u32 suffisent.
  • S'il n'y a aucun indice, le type par défaut est i32.
RègleAnnotations obligatoires pour les paramètres et le type de retour : la signature est un contrat lisible sans lire le corps, et ça accélère la compilation. Optionnelles pour les let quand le contexte suffit.

§1.3Le borrow checker

L'ownership et le borrowing ne sont présentés officiellement qu'au chapitre 03 (06_ownership, 10_references_in_memory), mais le borrow checker a déjà travaillé ici. C'est lui qui vérifie les règles d'accès aux valeurs : initialisation, mutabilité, propriété, emprunts.

Les 3 règles de l'ownership

  1. Chaque valeur a un seul propriétaire (une variable).
  2. Quand le propriétaire sort de sa portée (}), la valeur est détruite (drop). Pas de garbage collector.
  3. On peut emprunter une valeur via une référence : soit N références partagées &T (lecture seule), soit une seule référence mutable &mut T, jamais les deux en même temps.

C'est le principe « aliasing XOR mutation ». En plus, une référence ne doit jamais vivre plus longtemps que la valeur pointée (lifetimes).

Où tu l'as vu sans le savoir

SituationCe qui est vérifiéSi violé
let x: u32; let y = x + 1;Une variable doit être initialisée avant d'être lue.E0381
let sum = 0; sum += i; (ex. 06)On ne réassigne pas une variable non mut.E0384
fn factorial(mut n: u32)n est une variable locale ; mut rend ce nom modifiable.—
fn intro() -> &'static strLa référence retournée doit rester valide ; 'static = vit tout le programme (texte gravé dans le binaire).erreur de lifetime
let y = x; puis x, avec x: u32OK : u32 est Copy.—
let t = s; puis s, avec s: Strings a été déplacé (move), il n'est plus propriétaire.E0382

Copy ou move : pourquoi tes entiers « marchent tout seuls »

  • Les primitifs (u32, i8, bool, char…) sont Copy : petits, sur la pile, copiés bit à bit. Passer n à factorial(n - 1) ou appeler start.abs_diff(end) copie la valeur. L'original reste utilisable.
  • Un String possède de la mémoire sur le tas, donc il n'est pas Copy : une affectation déplace la propriété. C'est là que le borrow checker devient visible (chapitre 03).
let x: u32 = 42;
let y = x;                  // copie
println!("{x} {y}");        // ✅ x toujours valide

let s = String::from("a");
let t = s;                  // move : t devient propriétaire
println!("{s}");            // ❌ E0382 borrow of moved value: `s`

Ce qu'il faut savoir expliquer sur mut

  • mut est une propriété du nom (le binding), pas du type ni de la valeur.
  • fn f(mut n: u32) : l'appelant passe une copie, la fonction modifie sa copie locale. L'appelant ne voit rien. Ce n'est pas un passage par référence.
  • Pour modifier la variable de l'appelant : fn f(n: &mut u32) puis *n -= 1; (chapitre 03).
  • Pourquoi immuable par défaut ? « Aliasing XOR mutation » est bien plus facile à garantir si la mutation est explicite et rare. Et c'est plus lisible : un let sans mut ne changera jamais.
À savoir dire« Le borrow checker garantit à la compilation qu'aucune valeur n'est lue sans être initialisée, utilisée après avoir été déplacée ou détruite, ou modifiée pendant qu'un autre code la lit. C'est ce qui donne la sécurité mémoire sans garbage collector, sans coût à l'exécution. »

§2Aide-mémoire de syntaxe

// Commentaire simple
/// Commentaire de doc (attaché à l'item suivant → cargo doc --open)

// fn <nom>(<param>: <Type>, ...) -> <TypeRetour> { <corps> }
fn compute(a: u32, b: u32) -> u32 {
    let multiplier: u32 = 4;   // let <nom>: <Type> = <expr>;
    a + b * multiplier         // PAS de ; → valeur de retour
}

fn rien() { }                  // équivaut à fn rien() -> () { }

let mut x = 0;                 // variable modifiable
x += 1;                        // += -= *= /= %=

if cond { .. } else if cond2 { .. } else { .. }
let v = if cond { 1 } else { 2 };  // if est une EXPRESSION, branches du même type

while cond { .. }
for i in 1..=n { .. }          // inclusif
for i in 1..n  { .. }          // n exclu

panic!("message");             // ! = macro
todo!()                        // compile, mais panic à l'exécution

42u64          // littéral typé par suffixe
1_000_000      // underscores pour la lisibilité
x as u64       // conversion explicite

Instruction ou expression : le rôle du ;

  • Expression : produit une valeur (a + b, if … { 1 } else { 2 }, un bloc { … }).
  • Instruction : ne produit pas de valeur (let x = 5;, ou toute expression suivie de ;).
  • Le ; transforme une expression en instruction et jette sa valeur : le bloc vaut alors ().
  • return x sert au retour anticipé. En fin de fonction, le style idiomatique est d'écrire juste x.
fn f() -> u32 { 5 }    // ✅ renvoie 5
fn g() -> u32 { 5; }   // ❌ E0308 : le bloc vaut (), pas u32

§3Les exercices un par un

Clique sur un exercice pour voir ton code, le principe et les pièges.

00introFonctions et &'static str› 
fn intro() -> &'static str {
    "I'm ready to build a calculator in Rust!"
}

Fait : compléter la chaîne.

À expliquer : un littéral "..." est stocké dans le binaire. La fonction renvoie une référence (&) vers du texte (str) dont la durée de vie est 'static, c'est-à-dire tout le programme.

Tests : #[cfg(test)] = module compilé seulement pour cargo test ; #[test] marque une fonction de test ; assert_eq!(a, b) panique si différent ; use crate::intro importe depuis la racine du crate.

01integersTypes entiers, aucune conversion implicite› 
let multiplier: u32 = 4;   // était u8 → E0308
a + b * multiplier

Fait : passer multiplier de u8 à u32.

Principe : Rust refuse u32 * u8 même si la conversion serait sans perte. Toute conversion est explicite.

  • Opérateurs + - * / %, priorité mathématique.
Piège : / sur des entiers fait une division entière tronquée : 5 / 2 == 2.
02variables à nettoyerlet, annotation, inférence› 
let distance: u32 = start.abs_diff(end);
distance / time_elapsed

Fait : calculer la distance avec abs_diff (valeur absolue de la différence, jamais négative, donc jamais d'underflow). Solution attendue par le cours : let distance = end - start;.

« Faut-il annoter distance ? » Non : abs_diff sur un u32 renvoie un u32, le type est inféré. L'annotation est légale mais redondante.

Test case3 : speed(10, 31, 10) → 21 / 10 == 2 (division entière).

À nettoyer : use std::path::absolute; est inutile et déclenche un avertissement unused import. Sans doute ajouté par l'autocomplétion en tapant « abs ».
03if_elseBranchements et booléens› 
fn magic_number(n: u32) -> u32 {
    if n % 2 == 0 {
        return 12
    } else if n % 3 == 0 {
        return 13
    } else {
        return 17
    }
}
  • Principe : la condition doit être un bool. Pas de valeurs truthy/falsy comme en Python ou JavaScript.
  • L'ordre des tests compte : 6 est pair et divisible par 3 ; le test six attend 12 parce que le premier if gagne.
  • Comparaisons : == != < > <= >=. Logique : && || !.

Version idiomatique (if est une expression) :

fn magic_number(n: u32) -> u32 {
    if n % 2 == 0 { 12 } else if n % 3 == 0 { 13 } else { 17 }
}
04panics bug cachéErreur irrécupérable› 
if time_elapsed == 0 {
    panic!("The journey took no time at all. That's impossible!")
}
(end - start) / time_elapsed
  • Principe : un panic est une erreur irrécupérable. Le thread s'arrête, la pile est déroulée (unwinding) et les valeurs sont détruites proprement.
  • Diviser par zéro panique déjà tout seul (attempt to divide by zero) ; ici on remplace ce message par un message métier clair.
  • Test : #[should_panic(expected = "...")] réussit seulement si le code panique avec un message contenant ce texte.
  • panic! est une macro de type ! (« never ») : compatible avec n'importe quel type attendu, d'où la possibilité de la mettre dans un if sans else.
  • Plus tard (chapitre 05) : erreurs récupérables avec Result<T, E>.
Bug caché : end - start passe sous zéro si end < start (un u32 ne peut pas être négatif). Avec ton Cargo.toml actuel (overflow-checks = false), ce calcul ne panique plus : il renvoie silencieusement un nombre énorme. Correction : start.abs_diff(end) ou end.checked_sub(start).
05factorialRécursion› 
fn factorial(n: u32) -> u32 {
    if n == 0 { return 1 }
    else { return n * factorial(n - 1) }
}
  • Principe : un cas de base (0! = 1) et un cas récursif (n! = n × (n−1)!).
  • Pourquoi c'est sûr : quand n == 0, on ne calcule jamais n - 1, donc pas d'underflow.
  • Chaque appel empile un stack frame. Rust ne garantit pas l'optimisation des appels terminaux : pour de grandes profondeurs, préférer une boucle (risque de stack overflow).
  • Version idiomatique : if n == 0 { 1 } else { n * factorial(n - 1) }.
06whileBoucle et mut› 
pub fn factorial(mut n: u32) -> u32 {
    let mut res: u32 = 1;
    while n > 1 {
        res *= n;
        n -= 1;
    }
    res
}
  • Fait : un accumulateur res et un décrément de n. La condition n > 1 couvre 0! = 1 et 1! = 1 sans entrer dans la boucle.
  • Principe clé : mut obligatoire sur res et sur n, sinon E0384.
  • mut n dans les paramètres = la copie locale est modifiable (voir §1.3).
  • res renvoyé sans ; → valeur de retour.
Piège classique : while n >= 0 sur un u32 ne s'arrête jamais normalement : un u32 est toujours >= 0, et n -= 1 finit par passer sous zéro.
07forfor et ranges› 
pub fn factorial(n: u32) -> u32 {
    let mut res = 1;
    for i in 1..=n {
        res *= i;
    }
    res
}
  • Principe : for parcourt un itérateur. Plus de compteur manuel, donc moins de bugs (décalage d'un, oubli d'incrément).
  • i n'a pas besoin de mut : c'est une nouvelle variable à chaque tour.
  • n = 0 → 1..=0 est vide → on renvoie 1.
  • res est inféré u32 grâce à i: u32 et au -> u32.
SyntaxeContenuDans un for ?
1..51, 2, 3, 4 (5 exclu)oui
1..=51, 2, 3, 4, 5oui

08overflow réglage globalProfils Cargo et overflow-checks›

Aucune modification du lib.rs. Tout se passe dans le Cargo.toml racine :

[profile.dev]
overflow-checks = false
  • Problème : 20! = 2 432 902 008 176 640 000 ne tient pas dans un u32 (max ≈ 4,29 milliards).
  • Pas de promotion automatique vers un type plus grand (principe 2). Deux options : refuser (panic attempt to multiply with overflow) ou faire le tour (wrap) : on garde les 32 bits de poids faible, c'est-à-dire le résultat modulo 2³² → 2 192 834 560.
ProfilUtilisé paroverflow-checks par défaut
devcargo build, run, testtrue (panic)
release--releasefalse (wrap)
testhérite de dev—
benchhérite de release—

Pourquoi le Cargo.toml racine ? Le dépôt est un workspace (members = ["exercises/*/*"]) : les profils ne se configurent qu'à la racine du workspace et s'appliquent à tous les membres.

Conséquence : ce réglage vaut pour tous les exercices du dépôt. Le cours recommande plutôt overflow-checks = true, même en release : mieux vaut planter que produire un résultat faux. Le bloc [profile.dev.package.copy] existe justement pour forcer les checks sur un exercice à venir.
09saturatingChoisir au cas par cas› 
let mut result: u32 = 1;
for i in 1..=n {
    result = result.saturating_mul(i);
}

Principe : overflow-checks est un réglage global et grossier. Les méthodes permettent de choisir opération par opération.

MéthodeEn cas de dépassement255u8 + 1
+ (checks activés)panicpanic
+ (checks désactivés)wrap0
wrapping_addwrap, toujours0
saturating_addbloque à MAX ou MIN255

  • La saturation ne s'obtient que par les méthodes, jamais par un profil.
  • 20! saturé → u32::MAX = 4 294 967 295.
  • L'annotation : u32 est indispensable : appel de méthode sur un {integer} ambigu → E0689 (voir §1).
  • Une méthode est une fonction attachée à un type, appelée par valeur.methode(args) ; la valeur devient le premier argument (self). Ici self est un u32, donc copié.
10as_castingConversions explicites› 
let v: u32 = 47;   assert_eq!(47u16 as u32, v);  // élargissement, sans perte
let y: i8  = -1;   assert_eq!(255 as i8, y);     // mêmes bits, autre lecture
let v: u8  = 1;    assert_eq!(true as u8, v);    // true → 1, false → 0
  • as est infaillible : il produit toujours une valeur, même absurde.
  • Grand → petit : troncature. On garde les bits de poids faible : 256u16 as u8 == 0.
  • Même taille, signe différent : les bits ne changent pas, seule leur lecture change.

255 en mémoire :

11111111
  • Lu en u8 : 128 + 64 + … + 1 = 255.
  • Lu en i8 (complément à deux) : le bit de poids fort vaut −128, donc −128 + 127 = −1.
  • Pour obtenir −x : inverser tous les bits, puis ajouter 1.
  • #[allow(overflowing_literals)] désactive le lint qui refuse 255 as i8 sur un littéral. Sur une variable, le compilateur ne peut rien détecter.
Règle d'oras uniquement du petit vers le grand. Pour grand → petit : TryFrom / try_into() (chapitre 05), qui renvoie une erreur au lieu de mentir.

§4Overflow et underflow

  • Overflow : le résultat dépasse MAX. Underflow : il passe sous MIN (ex. 3u32 - 10).
  • Selon le contexte : panic (dev), wrap (release, overflow-checks = false, wrapping_*), saturation (saturating_*), Option (checked_*).
  • Pourquoi c'est grave : le contrat « u32 op u32 → u32 mathématiquement juste » est rompu. En fintech (montants, soldes), un wrap silencieux est catastrophique : préfère checked_* et traite le None.

§5Les tests en Rust

#[cfg(test)]               // compilé uniquement pour cargo test
mod tests {
    use crate::factorial;    // import depuis la racine du crate

    #[test]
    fn fifth() { assert_eq!(factorial(5), 120); }

    #[test]
    #[should_panic(expected = "impossible")]
    fn by_zero() { speed(0, 10, 0); }
}
  • cargo test -p <package> lance un seul exercice (nom dans le Cargo.toml de l'exercice, ex. while_).
  • #[...] est un attribut : une métadonnée pour le compilateur.
  • [lints.rust] dead_code = "allow" dans les Cargo.toml des exercices : pas d'avertissement pour les fonctions privées utilisées seulement par les tests.

§6Questions d'oral

Réponds à voix haute avant d'ouvrir la réponse.

Pourquoi let m: u8 = 4; a * m (avec a: u32) ne compile pas, alors qu'aucune information ne serait perdue ?
Rust ne fait aucune conversion implicite : les opérateurs exigent deux opérandes du même type. Il faut m as u32 ou typer m: u32.
Quelle différence entre 5 et 5; en fin de fonction ?
5 est une expression, donc la valeur de retour. 5; est une instruction : le bloc vaut (), d'où une erreur de type.
Pourquoi les paramètres de fonction doivent-ils être typés, et pas les let ?
La signature est un contrat : lisible sans lire le corps, elle permet de typer chaque fonction indépendamment (compilation plus rapide, erreurs localisées).
Pourquoi let mut r = 1; r = r.saturating_mul(i); ne compile pas, alors que r *= i compile ?
Un appel de méthode exige un type concret pour savoir quelle méthode appeler ; {integer} est ambigu → E0689. Un opérateur laisse l'inférence se terminer.
Que fait exactement fn f(mut n: u32) ? L'appelant voit-il la modification ?
n est une copie locale modifiable. L'appelant ne voit rien. Pour modifier sa variable : &mut u32.
Pourquoi let y = x; puis utiliser x marche avec un u32 mais pas avec un String ?
u32 est Copy (copie bit à bit). String possède de la mémoire sur le tas : l'affectation est un move et l'ancienne variable est invalidée (E0382).
Quelles sont les 3 règles de l'ownership ? Que signifie « aliasing XOR mutation » ?
Un seul propriétaire ; destruction à la fin de la portée ; N références & OU une seule &mut. On ne peut pas à la fois partager et modifier une valeur.
Que vaut factorial(20) en u32 : en dev par défaut ? avec overflow-checks = false ? avec saturating_mul ?
Panic (attempt to multiply with overflow) ; 2 192 834 560 (modulo 2³²) ; u32::MAX = 4 294 967 295.
Pourquoi modifier le Cargo.toml racine et pas celui de l'exercice ?
Le dépôt est un workspace Cargo : les profils ne se configurent qu'à la racine du workspace.
Pourquoi 255 as i8 == -1 ? Explique avec les bits.
Les bits 1111 1111 sont conservés. Lus en complément à deux, le bit de poids fort vaut −128 : −128 + 127 = −1.
Pourquoi as est-il dangereux, et que faut-il utiliser pour grand → petit ?
Il tronque ou réinterprète sans prévenir. Utiliser TryFrom / try_into(), qui renvoie une erreur.
Quel bug reste caché dans speed à l'ex. 04 ? Comment le corriger ?
end - start passe sous zéro si end < start. Corriger avec start.abs_diff(end) ou end.checked_sub(start).
panic! ou Result : quand utiliser l'un ou l'autre ?
panic! : bug ou état impossible, irrécupérable. Result : échec prévisible que l'appelant doit gérer.
Pourquoi Rust est-il immuable par défaut ?
Pour rendre la mutation explicite et rare : code plus lisible, garantie « aliasing XOR mutation » facile à vérifier à la compilation, et concurrence plus sûre.
