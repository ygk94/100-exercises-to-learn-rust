Fiche synthèse : Ticket v2

Le chapitre des enums et de la gestion d'erreurs. Le Ticket du chapitre 03 vérifiait tout à l'exécution avec des panic!. Ici on fait porter les règles par les types : un statut ne peut plus être invalide, une valeur absente devient Option, un échec devient Result, et chaque erreur a son propre type.

§0Les premiers principes du chapitre

Le chapitre 03 protégeait le Ticket par des vérifications. Le chapitre 05 le protège par des types.

principe 1

Rendre l'invalide impossible

Un String peut contenir "Dnoe". Un enum Status ne peut valoir que ses variantes. L'erreur passe de l'exécution à la compilation.

principe 2

match est exhaustif

Tous les cas doivent être traités. Ajouter une variante fait apparaître une erreur à chaque match à compléter.

principe 3

Pas de null

Une valeur qui peut manquer s'écrit Option<T> : Some(v) ou None. Impossible d'oublier le cas vide.

principe 4

Une erreur est une valeur

Result<T, E> : Ok(v) ou Err(e). La signature annonce que ça peut échouer, et l'appelant décide quoi faire.

principe 5

Valider une seule fois

Un TicketTitle qui ne se construit que via TryFrom est valide par construction. Plus besoin de revérifier ailleurs.

À savoir dire« En Rust, on encode les règles métier dans les types : un enum pour un ensemble fermé de valeurs, Option pour l'absence, Result pour l'échec. Le compilateur force alors à traiter chaque cas, au lieu de découvrir l'oubli en production. »

§1Enums et match

Un enum : une valeur parmi une liste fermée

#[derive(Debug, PartialEq, Clone, Copy)]
enum Status {
    ToDo,
    InProgress,
    Done,
}

let s = Status::Done;      // on nomme toujours Type::Variante
  • Avant : status: String + un if status != "To-Do" && … qui paniquait à l'exécution. Après : status: Status, et Status::Dnoe ne compile pas.
  • Les derive sont récursifs : pour dériver PartialEq sur Ticket, il faut que Status l'ait aussi.
  • Un enum sans données peut être Copy. Un Ticket qui contient des String, non (E0204).

match : un if sur les variantes

match self {
    Shape::Circle => 0,
    Shape::Square | Shape::Rectangle => 4,   // | = l'un ou l'autre
    Shape::Triangle => 3,
    Shape::Pentagon => 5,
}
  • Testé de haut en bas ; le premier motif qui correspond gagne. On exécute ce qui est après => (une expression, ou un bloc { … } si plusieurs lignes).
  • match est une expression : il renvoie une valeur. En dernière position d'une fonction, sans ;, c'est le retour.
  • Exhaustif : oublier une variante donne E0004 non-exhaustive patterns.
  • _ => … attrape « tout le reste ». Pratique, mais on perd l'alerte du compilateur si une variante est ajoutée plus tard.

Variantes avec données

enum Status {
    ToDo,
    InProgress { assigned_to: String },   // cette variante transporte un nom
    Done,
}

match &self.status {
    Status::InProgress { assigned_to } => assigned_to,   // le motif SORT la donnée
    _ => panic!("Only `In-Progress` tickets can be assigned to someone"),
}
  • Le motif InProgress { assigned_to } teste la variante et range le champ dans une variable assigned_to.
  • match &self.status : on emprunte, donc assigned_to est un &String (pas de move hors de self).
  • Deux formes : Variante { champ: T } (champs nommés) ou Variante(T) (tuple, comme TitleError(String) ou Some(v)).

if let et let … else : un seul cas intéressant

if let Shape::Circle { radius } = self {
    *radius                          // &f64 → f64
} else {
    panic!("Not a circle")
}                                    // ⚠ pas de ; ici : c'est la valeur de retour

// variante let/else : sortir tôt si ça ne correspond pas
let Shape::Circle { radius } = self else {
    panic!("Not a circle")
};
*radius
Piège rencontré : un ; après la dernière accolade transforme l'expression en instruction. La fonction renvoie alors () au lieu de f64 : mismatched types.

§2Option : peut-être une valeur

// défini dans std, dans le prelude
enum Option<T> {
    Some(T),
    None,
}

pub fn assigned_to(&self) -> Option<&String> {
    match &self.status {
        Status::InProgress { assigned_to } => Some(assigned_to),
        _ => None,
    }
}
  • Rust n'a pas de null. L'absence est un cas visible dans le type : impossible d'utiliser la valeur sans avoir traité None.
  • Comparé à l'exo 03 : au lieu de paniquer, on renvoie None et c'est l'appelant qui décide.
  • Méthodes utiles : .is_some(), .is_none(), .unwrap() (panique si None).

§3Result : réussite ou erreur

enum Result<T, E> {
    Ok(T),     // succès, voici la valeur
    Err(E),    // échec, voici pourquoi
}

pub fn new(title: String, …) -> Result<Ticket, String> {   // ① le type de retour change
    if title.is_empty() {
        return Err("Title cannot be empty".to_string());     // ② panic! → return Err(...)
    }
    …
    Ok(Ticket { title, description, status })               // ③ le succès est emballé
}

panic! ou Err ?

panic!Err(...)
Effetle programme (thread) s'arrêteune valeur est renvoyée, le programme continue
Qui décidepersonne, c'est finil'appelant (afficher, réessayer, valeur par défaut…)
Visible dans la signaturenonoui : -> Result<T, E>
Pourbug, situation impossibleerreur prévisible (saisie invalide, fichier absent…)
  • Une fonction ne renvoie qu'un seul type. Une erreur n'est pas un Ticket, d'où Result<Ticket, String> qui peut contenir l'un ou l'autre.
  • Tout ce qui sort doit être un Result, y compris le succès : d'où Ok(...). Même idée que Some(...).
Piège rencontré : garder -> Ticket dans la signature tout en écrivant return Err(...) donne mismatched types expected Ticket, found Result<_, String>.

Récupérer la valeur

match Ticket::new(title.clone(), description, status.clone()) {
    Ok(ticket) => ticket,
    Err(error) => panic!("{}", error),
}

r.unwrap()          // Ok(v) → v ; Err → panique (exige E: Debug)
r.expect("msg")     // pareil, avec ton message
r.unwrap_err()      // l'inverse : Err(e) → e ; Ok → panique (utilisé dans les tests)
r.is_ok() / r.is_err()

let status = Status::try_from(status)?;   // ? : Ok(v) → v ; Err(e) → return Err(e.into())
  • ? ne marche que dans une fonction qui renvoie elle-même un Result (ou Option). Il convertit l'erreur avec From/.into().
  • .clone() avant de passer title à new : sinon il est déplacé et on ne peut plus le réutiliser pour un second essai.

§4Des types d'erreur propres

Étape 1 : un enum d'erreurs

#[derive(Debug)]
enum TicketNewError {
    TitleError(String),
    DescriptionError(String),
}

match Ticket::new(…) {
    Ok(ticket) => ticket,
    Err(TicketNewError::TitleError(msg)) => panic!("{}", msg),
    Err(TicketNewError::DescriptionError(_)) => …,   // _ : je n'utilise pas le message
}

Avant on cherchait le mot « Description » dans le texte de l'erreur (error.contains(...)), ce qui est fragile. Maintenant la variante dit de quelle erreur il s'agit.

Étape 2 : Debug, Display, Error à la main

impl std::fmt::Display for TicketNewError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            TicketNewError::TitleError(msg) => write!(f, "{}", msg),
            TicketNewError::DescriptionError(msg) => write!(f, "{}", msg),
        }
    }
}

impl std::error::Error for TicketNewError {}   // bloc vide : tout a une valeur par défaut

Étape 3 : thiserror écrit tout ça pour toi

#[derive(Debug, thiserror::Error)]
enum TicketNewError {
    #[error("Title cannot be empty")]
    TitleCannotBeEmpty,
    #[error("Title cannot be longer than 50 bytes")]
    TitleTooLong,
    …
}
  • Le derive thiserror::Error génère impl Display (avec le texte de #[error("…")]) et impl Error.
  • Dans le message, {0} = premier champ d'une variante tuple, {nom} = champ nommé.
  • Il faut l'ajouter au Cargo.toml : thiserror = "1".

Étape 4 : chaîner les erreurs avec source

#[derive(Debug, thiserror::Error)]
pub enum TicketNewError {
    …
    #[error("{0}")]
    InvalidStatus(#[from] status::ParseStatusError),   // contient l'erreur d'origine
}

// dans new :
let status = Status::try_from(status)?;
  • #[from] marque le champ comme source : err.source() renvoie Some(...) au lieu de None.
  • Il génère aussi impl From<ParseStatusError> for TicketNewError, ce qui permet au ? de convertir l'erreur tout seul.
  • let status = … réutilise le nom : c'est du shadowing (nouvelle variable de type Status qui masque l'ancienne String).

§5TryFrom et newtypes validés

impl TryFrom<&str> for Status {
    type Error = String;                       // type associé, comme Add::Output

    fn try_from(value: &str) -> Result<Self, Self::Error> {
        match value.to_lowercase().as_str() {     // insensible à la casse
            "todo" => Ok(Status::ToDo),
            "inprogress" => Ok(Status::InProgress),
            "done" => Ok(Status::Done),
            _ => Err(format!("Invalid status: {}", value)),
        }
    }
}

impl TryFrom<String> for Status {
    type Error = String;
    fn try_from(value: String) -> Result<Self, Self::Error> {
        Status::try_from(value.as_str())          // réutilise la version &str
    }
}

  • TryFrom et TryInto sont dans le prelude depuis l'édition 2021 : pas de use.
  • .to_lowercase() crée une String ; .as_str() en fait un &str comparable aux littéraux du match.

Le newtype validé (exo 15)

#[derive(Debug, PartialEq, Clone)]
pub struct TicketTitle(String);              // champ privé : seul TryFrom peut le construire

impl TryFrom<String> for TicketTitle {
    type Error = TicketTitleError;
    fn try_from(value: String) -> Result<Self, Self::Error> {
        if value.is_empty() { return Err(TicketTitleError::Empty); }
        if value.len() > 50 { return Err(TicketTitleError::TooLong); }
        Ok(TicketTitle(value))
    }
}

pub struct Ticket {
    pub title: TicketTitle,                 // les champs peuvent devenir pub !
    pub description: TicketDescription,
    pub status: Status,
}

Chaque champ porte sa propre validation. Un TicketTitle qui existe est forcément valide, donc plus besoin de cacher les champs de Ticket derrière des getters/setters comme au chapitre 03. Exception : une règle qui concerne plusieurs champs à la fois obligerait à les rendre privés de nouveau.

  • Un package peut avoir main.rs et lib.rs. Le binaire importe la bibliothèque par le nom du package : use packages::hello_world; (la fonction doit être pub).
  • Un chemin d'import commence par le nom de la crate : use anyhow::Error;, thiserror::Error.

Un module dans son propre fichier

// src/lib.rs
mod status;                   // Rust va chercher src/status.rs
pub use status::Status;       // ré-export : les utilisateurs écrivent outro_04::Status

Le fichier porte le nom du module et se place dans le même dossier que le fichier qui le déclare. Le pattern « modules privés + pub use à la racine » cache l'organisation interne tout en exposant l'API.

§8Questions d'oral

Réponds à voix haute avant d'ouvrir la réponse.

Pourquoi un enum Status est-il meilleur qu'un status: String ?
Il ne peut valoir que ses variantes : une valeur invalide ne compile pas. Plus besoin de validation à l'exécution, et le compilateur vérifie chaque usage.
Que veut dire « match est exhaustif » ? Pourquoi c'est un avantage ?
Toutes les variantes doivent être traitées, sinon E0004. Si on ajoute une variante, le compilateur liste tous les match à mettre à jour (compiler-driven refactoring).
Que fait _ dans un match ? Quel est son inconvénient ?
Il attrape tous les cas non traités au-dessus. Inconvénient : une nouvelle variante tombe silencieusement dedans, sans alerte du compilateur.
Dans Status::InProgress { assigned_to } => assigned_to, que se passe-t-il ?
Le motif vérifie que c'est la variante InProgress et extrait son champ dans une variable assigned_to, utilisable après =>.
Pourquoi écrire match &self.status plutôt que match self.status ?
Pour emprunter : on ne peut pas déplacer la String hors de self qu'on ne possède pas. Avec &, les données extraites sont des références.
Quand utiliser if let plutôt que match ?
Quand un seul cas nous intéresse ; le reste va dans le else (ou rien). let … else sert à sortir tôt si le motif ne correspond pas.
Pourquoi un ; en trop à la fin d'une fonction casse-t-il le type de retour ?
La dernière expression sans ; est la valeur renvoyée. Avec ;, c'est une instruction : la fonction renvoie ().
Comment Rust représente-t-il l'absence de valeur ? Pourquoi pas de null ?
Option<T> : Some(v) ou None. L'absence est dans le type, donc on est obligé de la traiter ; pas de null pointer exception possible.
Différence entre panic! et renvoyer Err ?
panic! arrête le programme, l'appelant ne peut rien faire. Err est une valeur renvoyée : l'appelant décide (afficher, réessayer, valeur par défaut). On panique pour un bug, on renvoie Err pour une erreur prévisible.
Pourquoi faut-il changer le type de retour en Result<Ticket, String> et écrire Ok(...) ?
Une fonction ne renvoie qu'un type. Result peut contenir soit le ticket, soit l'erreur. Le succès doit donc aussi être emballé, dans Ok.
Que fait .unwrap() ? Pourquoi exige-t-il Debug sur l'erreur ?
Il sort la valeur d'un Ok/Some, et panique sur Err/None. En paniquant il affiche l'erreur avec {:?}, d'où Debug.
Que fait l'opérateur ? ?
Sur Ok(v) il donne v ; sur Err(e) il fait return Err(e.into()). Il ne marche que dans une fonction qui renvoie un Result/Option, et convertit l'erreur via From.
Pourquoi un enum d'erreurs vaut mieux qu'une String d'erreur ?
L'appelant distingue les cas par match sur la variante au lieu de chercher des mots dans un texte, ce qui est fragile.
Debug, Display, Error : rôle de chacun, lesquels peut-on dériver ?
Debug : affichage développeur {:?}, dérivable. Display : affichage utilisateur {}, à écrire (ou via thiserror). Error : marque une erreur, exige Debug + Display, bloc vide suffisant.
Qu'apporte thiserror ?
Un derive thiserror::Error qui génère Display à partir des #[error("…")] et impl Error, plus #[from]/#[source] pour chaîner les erreurs.
À quoi sert source() et que fait #[from] ?
source() donne l'erreur d'origine (chaîne de causes). #[from] la déclare comme source et génère un From, ce qui permet au ? de convertir automatiquement.
Différence entre From et TryFrom ?
From ne peut pas échouer et renvoie Self. TryFrom peut échouer et renvoie Result<Self, Self::Error>, avec un type associé Error.
Pourquoi l'exo 15 peut rendre les champs de Ticket publics ?
Chaque champ est un newtype qui ne peut exister que valide (construction via TryFrom uniquement). Aucune modification ne peut casser les règles, sauf une règle portant sur plusieurs champs.
Package, crate binaire, crate bibliothèque : différences ?
Package : dossier avec Cargo.toml. Binaire : src/main.rs avec main(). Bibliothèque : src/lib.rs, réutilisable, porte le nom du package. Un package peut avoir les deux.
Comment ajouter une dépendance ? Et mettre un module dans un fichier séparé ?
[dependencies] nom = "1" dans Cargo.toml (ou cargo add nom). Module : mod status; dans lib.rs + fichier src/status.rs.
