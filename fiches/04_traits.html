Fiche synthèse : Traits

Le chapitre des traits : des contrats qu'un type s'engage à respecter. C'est ce qui fait marcher ==, +, .into(), .clone(), l'affichage {:?} ou le nettoyage automatique. On y voit aussi les génériques et enfin la vraie différence entre String, &str et str.

§0Les premiers principes du chapitre

Le chapitre 03 créait des types. Le chapitre 04 leur donne des capacités communes.

principe 1

Un trait est un contrat

Il déclare des méthodes (nom, paramètres, retour) sans forcément les coder. Un type « signe » le contrat avec un impl.

principe 2

Les opérateurs sont des traits

a == b appelle PartialEq::eq, a + b appelle Add::add. Implémenter le trait, c'est faire marcher l'opérateur.

principe 3

Une seule implémentation possible

Jamais d'ambiguïté : une impl par couple (trait, type), et l'orphan rule empêche deux crates d'en écrire chacune une.

principe 4

Un générique nu ne sait rien faire

T peut être n'importe quel type. Les trait bounds disent ce que T sait faire, et c'est écrit dans la signature.

principe 5

Aucune conversion implicite

Même « évidente ». u32 → WrappingU32 exige un From. Seule exception notable : la deref coercion (&String → &str).

À savoir dire« Un trait définit un comportement partagé. Rust s'en sert à la fois pour la surcharge d'opérateurs, pour ajouter des méthodes à des types existants, et pour la programmation générique, où les trait bounds expriment ce qu'un type paramètre doit savoir faire. »

§1Définir et implémenter un trait

Les deux étapes

// 1. Le contrat : une déclaration, terminée par ;
trait IsEven {
    fn is_even(&self) -> bool;
}

// 2. Un type signe le contrat, et donne le code
impl IsEven for u32 {
    fn is_even(&self) -> bool {
        self % 2 == 0
    }
}

42u32.is_even()   // ✅   42u8.is_even() ❌ : u8 n'a pas signé
  • Un trait sans aucun impl ne sert à rien.
  • Un impl doit fournir tout ce que le trait exige (méthodes et types associés), avec des signatures identiques.
  • On écrit une impl par type : u32 et i32 → deux blocs.
  • Pas de pub devant les méthodes d'un impl Trait for Type (E0449) : la visibilité vient du trait.

Méthode par défaut

Un trait peut donner un corps à une méthode. Les impl la reçoivent gratuitement. Exemple réel, PartialEq (source simplifiée de core/src/cmp.rs) :

pub trait PartialEq<Rhs = Self> {
    fn eq(&self, other: &Rhs) -> bool;          // à écrire
    fn ne(&self, other: &Rhs) -> bool {         // par défaut
        !self.eq(other)
    }
}

On écrit seulement eq, et != marche tout seul.

Deux sortes d'impl

méthodes inhérentes

impl Ticket { … }

Pas de trait, noms libres. Réservé à tes types : impl u32 { … } est interdit (E0390).

C'est tout le chapitre 03 : new, getters, setters.

implémentation de trait

impl PartialEq for Ticket { … }

Noms imposés par le trait. Possible sur un type étranger si le trait est à toi.

Apporte une capacité standard : ==, +, .into(), {:?}…

Un même type a souvent les deux (ton WrappingU32 : impl WrappingU32 { fn new } + impl Add for WrappingU32). L'ordre des blocs dans le fichier n'a aucune importance.

Struct ou trait ?

Contientdes données (champs)des signatures de méthodes

§2Ce que Rust autorise : l'orphan rule

Une crate est un paquet de code : chaque exo en est une, et std aussi. « À toi » = défini dans ta crate.

Règle 1 : une seule impl par couple (trait, type)

Deux impl IsEven for u32 dans la même crate : E0119 conflicting implementations. Rust ne saurait pas laquelle appeler.

Règle 2 : l'orphan rule

Pour écrire impl Trait for Type, le trait OU le type doit être à toi.

TraitTypeAutoriséExemple
à toiétranger✅impl IsEven for u32 (exo 01)
étrangerà toi✅impl PartialEq for Ticket (exo 03) — le cas le plus courant
à toià toi✅impl IsEven for Ticket
étrangerétranger❌ E0117impl PartialEq for u32 (exo 02)

Pourquoi : si la crate B et la crate C écrivaient chacune impl IsEven for u32, un projet qui utilise les deux ne saurait pas laquelle choisir pour 4.is_even(). Avec la règle, seuls ceux qui possèdent le trait ou le type peuvent écrire l'impl : le conflit est impossible.

Extension trait : un trait créé pour ajouter des méthodes à un type étranger (IsEven pour u32). C'est le contournement officiel de l'interdiction impl u32 { … }.

Newtype : emballer un type étranger dans une struct à soi (WrappingU32 { value: u32 }) pour pouvoir lui donner d'autres comportements, par exemple un autre +.

§4Génériques et trait bounds

pub fn min<T: PartialOrd>(left: T, right: T) -> T {
    if left <= right { left } else { right }
}
  • <T> déclare un paramètre de type, un « type à trou ». Une seule fonction pour u32, i64, String…
  • Un T nu ne sait rien faire. Le bound T: PartialOrd dit : « n'importe quel type, à condition qu'il sache faire <= ».
  • Le bound est une contrainte, pas un appel : c'est <= qui appelle PartialOrd en coulisses.
  • Plusieurs bounds : T: IsEven + Debug (« et »). Syntaxe longue : where T: IsEven + Debug.
  • La signature est le contrat : le compilateur ne devine pas les bounds à partir du corps.
  • Tout générique est implicitement Sized. T: ?Sized lève cette contrainte (seul usage de ? dans un bound).

Générique ou type associé ?

paramètre générique

trait From<T>

Plusieurs impl pour un même type, une par T : From<u16> et From<u32> sont deux traits différents.

Pour : ce qui varie (type d'entrée).

type associé

type Target; / type Output;

Une seule valeur par impl : une String ne peut se « deref » qu'en str.

Pour : ce qui doit être déterminé sans ambiguïté (type de sortie).

Add combine les deux :

pub trait Add<Rhs = Self> {   // Rhs = "right-hand side", ce qu'on met à droite du +
    type Output;              // le type du résultat
    fn add(self, rhs: Rhs) -> Self::Output;
}
Un même nom de paramètre = un même type. Dans fn power(&self, n: Rhs) -> Rhs, l'entrée et la sortie seraient forcées au même type. C'est l'erreur de l'exo 10 : il fallait -> u32.

Pourquoi &str peut pointer au milieu

title : [ptr | len 14 | cap 14] &title[0..3] : [ptr | len 3] │ │ v v Tas : [ B | u | g | | l | o | g | i | n | | p | a | g | e ] └───────┘ "Bug" : on pointe dans la String existante, sans copie

Un &String ne peut désigner que la String entière. Pour renvoyer « Bug » en &String, il faudrait créer une nouvelle String.

  • Règle : on stocke une String (je possède) et on prête un &str (je montre). Getters en -> &str, paramètres en &str.
  • "To-Do" est un &'static str : un texte écrit dans le programme, qui existe toute l'exécution. D'où les .to_string() / .into() pour obtenir une String.

Deref coercion

String implémente Deref<Target = str>. Conséquences :

  1. un &String est converti automatiquement en &str quand il le faut (exo 06) ;
  2. toutes les méthodes de str qui prennent &self sont appelables sur une String : self.title.trim() (exo 07).

À ne pas abuser dans ses propres types : si T et sa cible ont une méthode du même nom, on ne sait plus laquelle est appelée.

Sized et fat pointers

  • str est un DST (dynamically sized type) : sa taille dépend du texte. size_of::<str>() ne compile pas.
  • Une référence vers un DST doit emporter la longueur avec elle : c'est un fat pointer (16 octets au lieu de 8).
  • Sized = « taille connue à la compilation ». C'est un marker trait (aucune méthode) et un auto trait (le compilateur l'ajoute seul). u32, String, &str sont Sized ; str ne l'est pas.

09fromFrom<u32> pour WrappingU32 (from)›

10assoc_vs_genericTrait Power générique (assoc_vs_generic)› 
trait Power<Rhs> {
    fn power(&self, n: Rhs) -> u32;
}

impl Power<u16>  for u32 { fn power(&self, n: u16)  -> u32 { self.pow(n as u32) } }

11cloneCloner avant de déplacer (clone)› 
pub fn summary(ticket: Ticket) -> (Ticket, Summary) {
    (ticket.clone(), ticket.summary())
}

#[derive(Clone)]
pub struct Ticket { … }
  • Le problème : (ticket, ticket.summary()) déplace ticket dans le tuple, puis le réutilise → E0382. Et summary(self) consomme le ticket.
  • Deux choses : rendre Ticket clonable (derive) et appeler .clone().
  • L'ordre compte (évaluation de gauche à droite) : (ticket.clone(), ticket.summary()) ✅, (ticket, ticket.clone().summary()) ❌.
  • clone fait une copie complète : nouvelle zone sur le tas, texte recopié.
La règleTant qu'une valeur n'a été que prêtée (&, &mut), elle est à toi : tu peux la cloner. Une fois déplacée (self, donnée à un tuple, une fonction, une variable), tu ne peux plus rien en faire. Le premier paramètre d'une méthode dit ce qui va arriver : &self je regarde, &mut self je modifie, self je garde.
12copyAdd + Copy pour WrappingU32 (copy)› 
use std::ops::Add;

#[derive(Debug, PartialEq, Clone, Copy)]

impl Add for WrappingU32 {

    }

  • Add fait marcher + ; x + y devient x.add(y).
  • Copy : le test utilise y deux fois. Sans Copy, le premier + le déplacerait.
  • PartialEq + Debug pour assert_eq!.
  • On garde impl WrappingU32 { fn new } et on ajoute impl Add : deux blocs différents.

13dropLa DropBomb (drop)› 
pub struct DropBomb {
    defused: bool,
}

impl DropBomb {
    pub fn new() -> Self { DropBomb { defused: false } }   // armée
    pub fn defuse(&mut self) { self.defused = true; }
}

impl Drop for DropBomb {
    fn drop(&mut self) {
        if !self.defused {
            panic!("Failed to defuse the bomb");
        }
    }
}
  • drop est appelé automatiquement à la fin de la portée. On n'écrit jamais bomb.drop().
  • Test 1 (#[should_panic]) : bombe non désamorcée → panic attendu. Test 2 : defuse() puis fin de portée → rien.
  • Usage réel : forcer une action (valider une transaction) ; si on l'oublie, le programme plante au lieu d'échouer en silence.
  • DropBomb est une struct, Drop est le trait.
Erreur rencontrée : tu avais écrit pub trait Drop { fn drop(&mut self); }. Ça crée un autre trait du même nom, que Rust n'appelle jamais à la destruction. Pour un trait de std, on implémente, on ne redéfinit pas.

§8Questions d'oral

Réponds à voix haute avant d'ouvrir la réponse.

Qu'est-ce qu'un trait ? À quoi sert-il en Rust (trois usages) ?
Un contrat de méthodes qu'un type peut implémenter. Usages : débloquer un comportement intégré (opérateurs, ==, +), ajouter des méthodes à des types existants (extension traits), et la programmation générique (trait bounds).
Différence entre impl Ticket { } et impl PartialEq for Ticket { } ?
Le premier définit des méthodes inhérentes, aux noms libres, uniquement sur ses propres types. Le second remplit le contrat d'un trait : noms imposés, possible sur un type étranger si le trait est à soi.
Énonce l'orphan rule et sa raison d'être.
Pour impl Trait for Type, le trait ou le type doit être défini dans la crate courante. Sans elle, deux crates pourraient implémenter le même trait pour le même type, et un projet qui utilise les deux ne saurait pas laquelle choisir.
Que fait réellement a == b ? Et a != b ?
PartialEq::eq(&a, &b) et PartialEq::ne(&a, &b). ne a une implémentation par défaut, !self.eq(other).
Pourquoi assert_eq! exige-t-il Debug ?
En cas d'échec, il affiche les deux valeurs comparées ; il faut savoir les représenter en texte.
Qu'est-ce que #[derive(...)] ? Quelle condition pour qu'il marche ?
Une macro qui génère l'impl du trait à partir des champs. Tous les champs doivent déjà implémenter le trait.
À quoi sert un trait bound ? Pourquoi le compilateur ne le devine-t-il pas ?
À dire ce qu'un type générique sait faire (T: PartialOrd pour utiliser <=). La signature est un contrat entre appelant et appelé : il doit être explicite (meilleurs messages d'erreur, doc, compilation plus rapide, moins de cassures).
Paramètre générique ou type associé : comment choisir ?
Générique quand on veut plusieurs impl pour un même type avec des entrées différentes (From<T>). Type associé quand le type doit être unique pour une impl donnée (Deref::Target, Add::Output).
String, &String, &str, str : taille et rôle de chacun ?
str : le texte, taille inconnue (DST). String : 24, texte possédé sur le tas. &String : 8, flèche vers une String entière. &str : 16, vue sur tout ou partie d'un texte (fat pointer).
Pourquoi préférer &str à &String dans un getter ou un paramètre ?
Plus souple : peut désigner une partie d'un texte, accepte les littéraux et les String, ne révèle pas le stockage interne.
Pourquoi fn title(&self) -> &str { &self.title } compile-t-il alors que &self.title est un &String ?
Deref coercion : String implémente Deref<Target = str>, donc &String est converti automatiquement en &str.
Pourquoi peut-on appeler trim() sur une String alors qu'elle est définie sur str ?
Grâce à Deref : les méthodes de str qui prennent &self sont accessibles sur une String.
Qu'est-ce que Sized ? Un marker trait ? Un auto trait ?
Sized marque les types de taille connue à la compilation. Marker trait : aucune méthode, juste une étiquette. Auto trait : le compilateur l'implémente tout seul.
Quel lien entre From et Into ?
Une blanket impl de std : si U: From<T>, alors T: Into<U>. On implémente From, on reçoit .into().
Différence entre Clone et Copy ? Pourquoi String ne peut pas être Copy ?
Clone : copie explicite (.clone()), potentiellement coûteuse. Copy : copie implicite, octet par octet, à la place du move. String gère du tas : une copie octet par octet donnerait deux propriétaires du même tas (double free).
Pourquoi un type avec un Drop ne peut-il pas être Copy ?
Un Drop signale une ressource à nettoyer. Des copies implicites exécuteraient le nettoyage plusieurs fois (E0184).
Dans (ticket, ticket.clone().summary()), pourquoi le clone ne sauve-t-il rien ?
Le tuple est évalué de gauche à droite : ticket est déjà déplacé quand on veut le cloner. Il faut cloner avant de déplacer.
Pourquoi ne met-on pas pub devant fn add dans impl Add for … ?
La visibilité des méthodes d'une impl de trait est celle du trait (E0449 sinon).
wrapping_add ou saturating_add ?
wrapping_add revient à 0 après le max ; saturating_add reste bloqué au max.
